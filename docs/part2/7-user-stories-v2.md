## 7. User stories v2

This page replaces the Part 1 user stories for Part 2. It applies the Part 1 feedback, re-ranks the stories, adds the stories that came out of building the app, and adds abuse stories for the ways a user might try to cheat. Each story names the automated test that checks it.

### Response to the Part 1 feedback

| Feedback | What we changed |
|---|---|
| The user stories lack the "why". | Every story now ends with **so that…**, stating the benefit to that actor. |
| What does "suitable activities" mean? | US-04 now defines it. An event is suitable when it is approved, not cancelled, still to come, not already booked and does not overlap one of the student's bookings. Suitable events are ranked by a stated score, and each card shows the reason for its place. |
| "It survives app restarts as Pending sync, without awarding points or a streak" needs clarifying. | US-11 now spells out what the student sees, what is counted (nothing until the server verifies the scan), when the upload happens (by itself, on reconnecting), and what happens on a restart. |
| What does "corrections recalculate the streak" mean? | US-15 now gives the rule and a worked example: a reversed event's week stops counting, and the streak is counted again without it. The test `reversal_recalculatesStreak` checks the example. |
| A device's clock can be manipulated, so how is that solved? | The server never uses the phone's clock to decide anything (US-12, AS-09). It checks the issue time signed into the QR code and its own receive time. The time the phone reports is kept only for diagnosis. The test `phoneClockIgnored_lateUploadStillRejected` checks this. |
| Separate the user stories and acceptance criteria into different columns. | Each table now has separate **User story** and **Acceptance criteria** columns. |
| Some acceptance criteria repeat the story. | The criteria now describe only what the system does, as Given / When / Then. |
| Acceptance criteria need clearer, measurable outcomes. | The criteria use exact values from `domain/Policy.kt`: 3 points, 5 active bookings, a 2-hour cut-off, 30-second codes, 5 code attempts and a 2-hour upload window. They also give the exact status or message the user sees. |
| Explain the intended benefits more clearly. | Covered by the **so that…** part of each story and by the new stories US-23 to US-28. |

### How to read the tables

**Priority:** **Must** means the app fails a requirement without it. **Should** means the app is weaker but still works. **Won't** means the story is dropped, with the reason.

**Status:** **Done** means it works in the app today on the in-memory backend. **Backend** means the screens and rules are done, and the server side lands with Firebase.

Tests in `ui/`, `data/` and `domain/` are JVM unit tests. `EndToEndTest` and `ScreenTests` run on the emulator.

### R3 · Secure and reliable attendance

| ID | User story | Acceptance criteria | Priority | Status | Tests |
|---|---|---|---|---|---|
| **US-08** | As a club committee member, I want to run check-in from my phone, so that students can prove they are in the room. | **When** I tap Start check-in, **then** a QR code and a 6-digit code appear, and both change every 30 seconds with a countdown.<br>**When** my phone goes offline, **then** no new code is shown and the screen says check-in is paused.<br>**When** I tap Open checkpoint, **then** a separate checkpoint code replaces the arrival code.<br>**When** I tap End check-in, **then** no more codes are issued, and scans saved offline are still accepted for 2 hours. | Must | Done | `codeRotatesEvery30Seconds`, `offline_pausesNewCodes`, `openCheckpoint_switchesStage`, `endCheckIn_closesSession` |
| **US-09** | As a student, I want to check in by scanning the event QR, so that my attendance is recorded in seconds in a crowded room. | **Given** I am booked and online, **when** I scan the live code and confirm with my fingerprint or screen lock, **then** that stage shows *Verified*.<br>**When** the code is more than one rotation old (over 60 seconds), **then** the result is "This QR code has expired…".<br>**When** the code was changed, is for another event or is the wrong stage, **then** the result is *Rejected* with that reason.<br>**When** I cancel the fingerprint prompt, **then** nothing is sent. | Must | Done | `scanOnline_stageVerified`, `expiredLiveToken_rejected`, `alteredToken_rejected`, `identityCancelled_sendsNothing` |
| **US-10** | As a student, I want to type a backup code when my camera fails, so that a broken camera doesn't cost me my attendance. | **When** I enter the live 6-digit code online, **then** the stage is *Verified*.<br>**When** I enter a wrong code, **then** I see the error and can try again, up to 5 times per session. | **US-28** | As the s-CPD office, I want committee members to earn no points for their own club's events, so that clubs can't award points to themselves. | **Given** a member of club A, **when** they check in at club A's event, **then** attendance is recorded and no points are added. | Should | Backend | Cloud Function test, planned |

### R4 · Online and offline

| ID | User story | Acceptance criteria | Priority | Status | Tests |
|---|---|---|---|---|---|
| **US-11** | As a student at a venue with no signal, I want my QR scan saved on my phone, so that a bad connection doesn't cost me my attendance. | **Given** no connection, **when** I scan a valid QR, **then** the stage shows *Saved on phone*, the result reads *Pending sync*, and points earned stay at 0.<br>**Then** Progress shows "1 check-in waiting to sync. Points appear once it's verified." Neither the total nor the streak changes until the server verifies the scan.<br>**When** the connection returns, **then** the app uploads the scan without me tapping anything, and the stage becomes *Verified* or *Rejected* with a reason.<br>**Then** the saved scan stays on the phone until the server answers. Keeping it after the app is closed needs the Room queue (Backend). | Must | Done; surviving a restart is Backend | `scanOffline_stagePendingSync_andChipSaysSavedOnPhone`, `claim_offline_returnsPendingSync_thenSyncVerifies`, `pendingClaims_shownAsNotYetCounted` |
| **US-12** | As a student, I want to know whether each saved scan counted and why, so that I can contact the organiser while it can still be fixed. | **When** a saved scan uploads, **then** the server accepts it only if the code was issued during that event's check-in and the upload arrives within 2 hours of check-in closing.<br>**Then** both checks use server time: the issue time is signed into the code, and the receive time is the server's own. The time the phone reports is kept only for diagnosis, so changing the phone's clock can't make a late scan count.<br>**When** a scan is rejected, **then** the record shows the reason, for example "Uploaded too late…".<br>**Then** the check-in screen shows "Last synced x min ago", and the same scan uploaded twice counts once. | Must | Done | `offlineScan_uploadedAfterDeadline_rejectedWithReason`, `phoneClockIgnored_lateUploadStillRejected`, `claim_sameRequestIdTwice_countsOnce` |
| **US-27** | As a student, I want a warning before I sign out with scans not yet synced, so that I don't lose points by accident. | **Given** 1 or more scans are saved on the phone, **when** I tap Sign out, **then** a dialog says how many would be lost, with *Stay signed in* as an option.<br>**Given** none are saved, **then** sign-out happens straight away. | Must | Done | `signOutWithPending_showsWarningFirst`, `signOutWithNoPending_signsOutDirectly` |

### R5 · Points and progress

| ID | User story | Acceptance criteria | Priority | Status | Tests |
|---|---|---|---|---|---|
| **US-14** | As a student, I want to see the points I have earned, so that I can track my progress towards the s-CPD requirement. | **When** every required stage of an event is *Verified* and the event requested points, **then** exactly 3 points are added once, however many times the claim is sent.<br>**Then** *Pending sync*, *Incomplete attendance*, *Rejected* and *No-show* add 0 points.<br>**Then** the Progress total equals the sum of the points history, and the ring shows the next milestone (15, 30, 60, 90, then every 30). | Must | Done | `bothStagesVerified_awardsThreePointsOnce`, `pointsOnlyForVerified`, `pointsAndStreak_fromLedgerAndHistory`, `milestoneIsTheNextTargetAbovePoints` |

### Abuse stories

Each abuse story is written from the cheater's side. The criteria say what the system must do. The defences and remaining weaknesses are in [8. Threat model](8-threat-model.md).

| ID | Abuse story | Acceptance criteria | Status | Tests |
|---|---|---|---|---|
| **AS-01** | As an absent student, I scan a photo of the QR that a friend sent me, while offline, so that I can upload it later and get points. | **When** the upload arrives more than 2 hours after check-in closed, **then** it is rejected with the reason. | Done | `offlineScan_uploadedAfterDeadline_rejectedWithReason` |
| **AS-02** | As a student, I sign out and back in on one phone to check in my friends, so that they get points without coming. | **When** a second account checks in with the same phone at the same event, **then** it is refused, and both accounts show *Flagged* to the committee. | Done | `claim_sameDeviceDifferentAccountsSameEvent_flagged`, `claim_includesDeviceId_soSharedPhoneIsFlagged` |
| **AS-03** | As a student, I hand my unlocked phone to a friend at the event, so that I get points while somewhere else. | **When** a check-in is about to be sent, **then** the phone asks for the fingerprint or screen lock, and cancelling sends nothing. | Done | `identityCancelled_sendsNothing` |
| **AS-04** | As an organiser, I post the live QR in my club's group chat, so that members get points without coming. | **Then** every claim is stored with its device, and flagged claims appear under the committee's Flagged filter. **Then** the office is alerted to check-ins outnumbering bookings or arriving in bursts (Backend). | Partly done | `attendees_flaggedFilterShowsReason` |
| **AS-05** | As a student, I book every event and don't turn up, so that I keep my options open. | **Then** the limits in US-24 apply: 5 active bookings, a 2-hour cancellation cut-off and a pause after 3 no-shows. | Done | `fiveActive_returnsCapReached`, `threeNoShows_returnsPaused` |
| **AS-06** | As a club, I create events just to give my members points. | **Then** no event is public until the office approves it (US-02), and members get no points for their own club's events (US-28, Backend). | Approval done; own-club rule is Backend | `committeeApproval_reachesStudentsStraightAway` |
| **AS-07** | As a student, I change a QR code or call the backend directly, so that I can fake a check-in. | **When** a code's signature doesn't match, **then** the claim is rejected as altered. **Then** only the signed-in account is trusted from the phone. | Done in the in-memory server; Firestore rules are Backend | `alteredToken_rejected` |
| **AS-08** | As a student, I guess backup codes until one works. | **When** 5 wrong codes are entered in one session, **then** backup codes are blocked for that student for the rest of the session. | Done | `claim_wrongBackupCodeFiveTimes_returnsRateLimited` |
| **AS-09** | As a student, I set my phone's clock back, so that a late offline scan looks as if it was made during the event. | **When** the scan uploads, **then** the server judges it by the issue time signed into the code and its own receive time, so it is rejected if it arrives more than 2 hours after check-in closed. | Done | `phoneClockIgnored_lateUploadStillRejected` |
